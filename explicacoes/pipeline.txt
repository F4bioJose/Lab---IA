########## EXPLICAÇÕES DO PROJETO TINY-CNN FPGA ##########

## VISÃO GERAL DO SISTEMA

A arquitetura implementa uma Rede Neural Convolucional (CNN) inteiramente em hardware, sintetizada na FPGA DE2-115 (Cyclone IV EP4CE115F29C7) como cerne do protótipo de Fechadura Biométrica Inteligente para a UFBA. O sistema recebe uma imagem 32×32 em escala de cinza via comunicação serial UART, executa a inferência completa através de um pipeline de processamento em hardware dedicado e exibe o resultado da classificação nos LEDs verdes da placa.

O sistema é composto por dois níveis hierárquicos de módulos Verilog:
- Nível Superior: `fpga_top_de2115.v` — Wrapper sintetizável que mapeia os pinos físicos da DE2-115 (clock, botões, UART, LEDs) e instancia o pipeline CNN.
- Nível Inferior: `cnn_top.v` — Orquestrador do pipeline computacional, contendo a FSM de inferência e todas as instâncias dos submódulos da rede neural.


## FLUXO DE DADOS COMPLETO: DO PC AOS LEDs

O percurso dos dados, do computador do operador até a decisão final exibida nos LEDs, segue a seguinte cadeia:

   PC (script Python)
     │  Envia 1024 bytes via cabo serial RS-232
     ▼
   Pino UART_RXD (PIN_AB21 da DE2-115)
     │  Sinal serial 115200 baud, 8N1
     ▼
   fpga_top_de2115.v (wrapper)
     │  Repassa rx_pin ao cnn_top
     ▼
   uart_rx (dentro do cnn_top)
     │  Decodifica start bit, 8 data bits, stop bit
     │  Emite uart_data[7:0] + uart_valid (pulso de 1 ciclo por byte)
     ▼
   Lógica de Escrita UART (dentro do cnn_top)
     │  Combinacional: uart_wr_en_comb = uart_valid & IDLE & !frame_ready
     │  Escreve uart_data no framebuffer no endereço uart_wr_addr
     │  Incrementa uart_wr_addr a cada byte (0 → 1023)
     │  Ao atingir 1023: seta uart_frame_pending
     ▼
   framebuffer_32x32.v
     │  Armazena os 1024 pixels em RAM behavioral (mem_a + mem_b espelhados)
     │  Quando endereço 1023 é escrito: frame_ready ← 1
     ▼
   FSM Principal (cnn_top)
     │  Detecta frame_ready + uart_start_pulse → transição ST_IDLE → ST_READ
     │  Emite frame_clear para consumir o frame_ready
     │  Varre endereços 0..1023 lendo do framebuffer, 1 pixel/ciclo
     ▼
   line_buffer_32x32.v
     │  Recebe fluxo de pixels e mantém 2 linhas de atraso (row1, row2)
     │  Gera janela 3×3 contígua a cada ciclo (válida a partir do pixel [2,2])
     ▼
   conv_4_filters_relu_window (convolucao_mac.v)
     │  4 filtros 3×3 paralelos: MAC(janela, pesos) + bias
     │  Ativação ReLU com saturação para Q2.14
     │  Produz 4 canais de saída simultâneos
     ▼
   max_pooling_design.v
     │  Redução 2×2 em cada canal: extrai o máximo de 4 vizinhos
     │  Controle via FIFO interna para sincronizar linhas
     │  Serializa os 4 canais via multiplexador temporal
     ▼
   flatten.v
     │  Repassa os dados sem transformação (identidade)
     │  Conta 900 elementos (4 canais × 15 × 15) e sinaliza done
     ▼
   dense_900x7_scores (dense_900x7.v)
     │  7 acumuladores paralelos processam 900 entradas sequencialmente
     │  Cada entrada: x_in × w_in[classe] acumulado em precisão Q3.21
     │  Ao final: adiciona bias, desloca para Q2.14, satura
     │  Emite 7 scores brutos + done
     ▼
   argmax_threshold_7.v
     │  Identifica o maior score entre os 7 (argmax)
     │  Compara com limiar THRESH_Q2_14 (0.7 de confiança)
     │  Emite class_id[2:0], unknown, max_score[15:0]
     ▼
   FSM Principal (cnn_top)
     │  Detecta dense_done → ST_DONE → access_done = 1 (1 ciclo)
     ▼
   fpga_top_de2115.v (latch dos LEDs)
     │  Captura class_id, unknown no instante de access_done
     │  LEDG[2:0] ← class_id, LEDG[6] ← 1, LEDG[7] ← unknown
     ▼
   LEDs verdes (LEDG) da DE2-115
     Exibem o resultado indefinidamente até reset ou nova inferência.


## DETALHAMENTO DOS MÓDULOS DE HARDWARE

1. Wrapper Top-Level (`fpga_top_de2115.v`):
O módulo mais externo da hierarquia, único visível para o sintetizador como entidade de topo. Recebe os sinais físicos da placa DE2-115: o oscilador de 50 MHz (CLOCK_50), dois botões (KEY[0] para reset, KEY[1] para disparo manual), o pino de recepção serial (UART_RXD) e os 8 LEDs verdes (LEDG[7:0]). Sua função principal é instanciar o `cnn_top`, conectar os pinos aos barramentos internos, e implementar o registrador de captura (latch) que preserva o resultado da classificação nos LEDs. O botão KEY[1] passa por um pipeline de sincronização de 3 estágios com detecção de borda de descida para gerar um pulso limpo de 1 ciclo, conectado à entrada `start_system` do `cnn_top`.

2. Receptor UART (`uart_rx.v`):
Módulo de comunicação serial responsável por receber os bytes transmitidos pelo computador. Implementa uma máquina de estados de 4 estágios (IDLE, START, DATA, STOP) que opera no domínio do clock de 50 MHz. Parametrizado com CLK_FREQ=50000000 e BAUD_RATE=115200, calcula automaticamente o número de ciclos por bit (CYCLES_PER_BIT = 434). No estado START, amostra o bit no meio do período para rejeitar ruídos transitórios. No estado DATA, captura 8 bits sequencialmente (LSB primeiro) em um shift register. Ao completar o stop bit, transfere o byte montado para `data_out[7:0]` e pulsa `data_valid` por exatamente 1 ciclo.

3. Framebuffer (`framebuffer_32x32.v`):
Memória de armazenamento temporário para a imagem de entrada. Implementa 1024 posições de 8 bits cada, utilizando duas RAMs comportamentais espelhadas (mem_a e mem_b) para permitir leituras simultâneas independentes: uma para o pipeline da CNN e outra para o futuro controlador VGA. A escrita é unificada — dados enviados para ambas as memórias no mesmo ciclo. A detecção de imagem completa ocorre quando o endereço de escrita atinge 1023, momento em que a flag `frame_ready` é levantada. O sinal `frame_clear` consome esta flag para prevenir re-disparos. Em simulação, as RAMs são inicializadas com zeros; em síntese, o Quartus as inferirá como blocos M9K.

4. Line Buffer (`line_buffer_32x32.v`):
Buffer de linhas que transforma o fluxo unidimensional de pixels proveniente do framebuffer em janelas bidimensionais de 3×3 elementos. Internamente, mantém duas linhas de atraso (row1 e row2), cada uma com 32 posições. A cada novo pixel recebido (controlado por `shift_en`), o conteúdo das linhas desliza (shift register) e uma nova coluna é preenchida: `win[2] ← row2[x]` (linha superior), `win[5] ← row1[x]` (linha intermediária) e `win[8] ← pixel_in` (linha atual). Contadores de posição (in_x, in_y) rastreiam as coordenadas bidimensionais do pixel corrente. Uma janela válida só é produzida a partir da posição (2,2), quando existem dados suficientes nas três linhas para compor a vizinhança completa.

5. Convolução MAC (`convolucao_mac.v`):
Núcleo de processamento espacial. Recebe a janela 3×3 do Line Buffer e executa simultaneamente 4 operações de Multiplicação e Acumulação (MAC) — uma por filtro. Cada MAC calcula o produto escalar entre os 9 elementos da janela e os 9 pesos do filtro correspondente, todos em formato Q1.7 (8 bits com sinal, 7 bits fracionários). O resultado intermediário (20 bits) recebe a adição do termo de viés (bias), extensionado de Q1.7 para a mesma escala. A função ReLU é aplicada: valores negativos são zerados, valores positivos são saturados no limite de Q2.14 (16 bits, máximo 32767). Os 4 canais de saída são registrados e validados em sincronia com o sinal `window_valid`.

6. Max Pooling (`max_pooling_design.v`):
Módulo de redução dimensional. Opera sobre janelas de 2×2 pixels em cada um dos 4 canais convolucionais, extraindo o valor máximo. O controle de vizinhança utiliza buffers internos de 30 posições (dimensão 30 = largura da imagem convoluída de 30 pixels: 32 − 3 + 1) para armazenar a linha anterior de cada canal. A geração de eventos de pooling ocorre em posições onde tanto x quanto y são ímpares (x[0] && y[0]). Uma FIFO de 32 posições (64 bits por entrada, empacotando os 4 canais) acumula os resultados de pooling. A serialização posterior utiliza um multiplexador de 4 canais (chan_idx) que entrega um canal por ciclo de clock, produzindo um fluxo contínuo de saída.

7. Flatten (`flatten.v`):
Interface de transição entre o domínio espacial (mapas 2D × canais) e o domínio linear (vetor 1D). Parametrizado com CHANNELS=4, HEIGHT=15, WIDTH=15, totalizando TOTAL_SIZE=900 elementos. O módulo repassa transparentemente os dados de entrada para a saída, acrescentando apenas um contador que detecta o último elemento (posição 899) e emite um pulso `done` de 1 ciclo. Este pulso é essencial para a camada densa saber quando todos os dados foram recebidos.

8. Camada Densa (`dense_900x7.v`):
Camada completamente conectada (Fully Connected) que mapeia as 900 características extraídas pelo pipeline convolucional em 7 escores de classificação. Possui 7 acumuladores paralelos (um por classe), cada qual operando em precisão estendida Q3.21 (48 bits) para prevenir overflow durante a acumulação de 900 produtos. A cada ciclo válido, todos os 7 pesos da coluna corrente (endereçados por `dense_addr`) são multiplicados pela entrada `x_in` e acumulados simultaneamente. No 900º elemento, os termos de viés (bias) são adicionados, seguidos de um deslocamento aritmético de 7 bits à direita (>>>7) para reenquadrar o resultado no formato Q2.14 (16 bits). Os valores são saturados nos limites [-32768, +32767]. Os 7 scores finais ficam disponíveis nas saídas `scores[0..6]` simultaneamente com os pulsos `valid_out` e `done`.

9. Argmax e Threshold (`argmax_threshold_7.v`):
Módulo de decisão final. Avalia os 7 scores recebidos da camada densa e determina qual classe possui a maior ativação (argmax). O processo é puramente combinacional dentro de um loop: inicializa com `scores[0]` e compara sequencialmente com `scores[1]` até `scores[6]`. O vencedor é armazenado em `max_idx`. Em seguida, o valor máximo é comparado contra o limiar de confiança parametrizado `THRESH_Q2_14` (padrão: 11469, equivalente a ≈0.70 em Q2.14). Se o score máximo for inferior ao limiar, o módulo atribui `class_id = 7` e `unknown = 1` (classificação incerta). Caso contrário, confirma o índice da classe vencedora e `unknown = 0`.

10. Memória de Pesos (`weights_shared_rom.v`):
Memória ROM estática que consolida todos os parâmetros pré-treinados da rede neural em um único array linear de 6347 palavras de 8 bits. O layout interno é:
- Endereços 0–35: Pesos dos 4 filtros convolucionais (4 × 9 = 36 valores).
- Endereços 36–39: Vieses (bias) dos 4 filtros convolucionais.
- Endereços 40–6339: Pesos da camada densa (900 × 7 = 6300 valores), organizados por classe.
- Endereços 6340–6346: Vieses (bias) das 7 classes da camada densa.
Os pesos da convolução são acessados estaticamente via assign combinacional. Os pesos da camada densa são acessados dinamicamente pelo endereço `dense_addr`, que percorre 0 a 899 durante a inferência. A inicialização é feita pelo arquivo `weights_all.mif` — em síntese, o Quartus utiliza a diretiva `ram_init_file`; em simulação, o bloco `initial` faz parse manual do arquivo MIF.

11. Controlador de Pipeline (`cnn_top.v`):
Módulo orquestrador que instancia e interconecta todos os submódulos acima. Incorpora o receptor UART, a lógica de escrita no framebuffer, a FSM principal de 4 estados (ST_IDLE, ST_READ, ST_WAIT, ST_DONE), e o controle de endereçamento da ROM de pesos densos. O cnn_top recebe da camada superior (fpga_top_de2115) o clock, reset, pino UART e sinal de start manual, e devolve os sinais de resultado (class_id, unknown, final_result, access_done, frame_ready). Toda a documentação da FSM encontra-se no arquivo `explicacoes/FSM.md`.


## FORMATO DE PONTO FIXO

A arquitetura emprega dois formatos de ponto fixo para representar valores numéricos sem hardware de ponto flutuante:

- Q1.7 (8 bits): Utilizado para pesos e vieses. 1 bit de sinal, 0 bits inteiros, 7 bits fracionários. Intervalo representável: [-1.0, +0.9921875]. Resolução: 1/128 ≈ 0.0078125.

- Q2.14 (16 bits): Utilizado para ativações intermediárias e scores finais. 1 bit de sinal, 1 bit inteiro, 14 bits fracionários. Intervalo representável: [-2.0, +1.99993896484375]. Resolução: 1/16384 ≈ 0.000061035.

- Q3.21 (48 bits): Utilizado internamente nos acumuladores da camada densa durante a fase de multiplicação-acumulação. Este formato estendido é necessário para prevenir overflow ao somar 900 produtos. Após a acumulação completa, o resultado é reenquadrado para Q2.14 via deslocamento aritmético de 7 bits à direita.


## SCRIPT PYTHON PARA ENVIO DE IMAGEM

O script `scripts/send_image_32x32.py` é a interface entre o computador do operador e a FPGA. Ele prepara uma imagem para a resolução esperada pela rede (32×32 grayscale) e a transmite via porta serial RS-232.

Modos de operação:
- Arquivo estático (imagem): `python3 send_image_32x32.py --file foto.jpg` — Carrega a imagem, opcionalmente detecta e recorta o rosto via Haarcascade, redimensiona para 32×32 e envia.
- Arquivo estático (hex): `python3 send_image_32x32.py --file inputs/teste2.txt --hex` — Carrega um arquivo texto contendo 1024 valores hexadecimais (um por linha) e envia os bytes correspondentes.
- Webcam: `python3 send_image_32x32.py` — Captura um único frame da webcam, aplica CLAHE para normalização de iluminação, detecta rosto e envia.
- Modo mock: `python3 send_image_32x32.py --mock --file foto.jpg` — Simula o envio sem abrir a porta serial (útil para testes sem a placa).

Parâmetros ajustáveis: porta serial (--port, padrão /dev/ttyUSB0), baud rate (--baud, padrão 115200), índice da câmera (--camera, padrão 0), preview visual (--preview).


## PROJETO QUARTUS PARA SÍNTESE

O diretório `quartus_cnn/` contém os três arquivos necessários para abrir e compilar o projeto no Quartus Prime:

- `cnn_inference.qpf`: Arquivo de projeto (Project File).
- `cnn_inference.qsf`: Configurações e atribuições de pinos (Settings File). Define o dispositivo alvo (EP4CE115F29C7), todos os pinos utilizados (CLOCK_50, KEY[0:1], UART_RXD, LEDG[7:0]), os padrões de I/O (3.3V LVTTL para clock e UART, 2.5V para botões e LEDs), e a lista de arquivos fonte Verilog.
- `cnn_inference.sdc`: Timing Constraints (Synopsys Design Constraints). Define o clock de 50 MHz e marca como false path os sinais assíncronos (UART, botões, LEDs).


## PROCEDIMENTO DE SIMULAÇÃO E VALIDAÇÃO RTL

A validação da coerência estrutural da implementação em nível RTL ocorre mediante scripts TCL no ambiente ModelSim. O testbench `tb_fpga_top.v` simula o fluxo completo do sistema, desde a recepção UART até a exibição nos LEDs.

1. Estabeleça o diretório do terminal do ModelSim na pasta raiz do repositório.
2. Inicie a compilação de todos os módulos Verilog:
   do scripts/compile_project.do
3. Execute a simulação:
   do scripts/run_project.do

O testbench realizará automaticamente:
- Reset do sistema (simula pressionamento de KEY[0]).
- Envio de 1024 bytes via protocolo UART serial (simulando o script Python).
- Monitoramento das transições da FSM (ST_IDLE → ST_READ → ST_WAIT → ST_DONE).
- Exibição dos scores finais das 7 classes e do resultado de classificação no console.
- Verificação de que os LEDs refletem corretamente o resultado.

O baud rate do testbench é acelerado (1 Mbaud em vez de 115200) para reduzir o tempo de simulação. Isso não afeta a lógica funcional.


## PROCEDIMENTO DE SÍNTESE E PROGRAMAÇÃO DO FPGA

1. Abra o Quartus Prime e carregue o projeto: File → Open Project → `quartus_cnn/cnn_inference.qpf`.
2. Execute a compilação completa: Processing → Start Compilation (ou Ctrl+L).
3. Após a compilação bem-sucedida, programe a FPGA via JTAG: Tools → Programmer → selecione o arquivo `output_files/cnn_inference.sof` → Start.
4. Pressione KEY[0] na placa para garantir um reset limpo.
5. Execute o script Python no PC para enviar a imagem:
   python3 scripts/send_image_32x32.py --file inputs/teste2.txt --hex --port /dev/ttyUSB0
6. Observe os LEDs verdes da placa. LEDG[6] acenderá quando a inferência concluir. LEDG[2:0] indicarão a classe predita em binário.


## DIRETRIZES DE INTEGRAÇÃO FUTURA (VGA + VÍDEO CONTÍNUO)

A arquitetura foi projetada para suportar expansão incremental:

Integração VGA:
O framebuffer atual (framebuffer_32x32.v, 1024 bytes) é independente do framebuffer utilizado na branch "terceira_entrega" (altsyncram 4096 bytes, 64×64). Na integração final, será necessário introduzir um esquema de arbitragem onde a imagem recebida pela UART seja armazenada em dois buffers: um de resolução maior para exibição VGA e outro de 32×32 para alimentação da CNN (possivelmente com downscale por hardware).

Vídeo Contínuo:
O pipeline CNN e a FSM do cnn_top já suportam inferências sequenciais: basta enviar uma nova imagem de 1024 bytes pela UART para que o ciclo completo se repita. O script Python poderá ser adaptado para modo contínuo (captura de webcam em loop), transformando o sistema em classificador em tempo real.
